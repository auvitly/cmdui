# Техническое задание: веб-интерфейс для запуска команд

## 1. Назначение

Разработать приложение на Go, которое предоставляет веб-интерфейс для авторизованного запуска команд. Приложение должно разграничивать доступ по ролям и позволять администратору управлять командами и проверять их перед публикацией операторам.

## 2. Роли и права доступа

### Оператор

- Может войти в приложение и выйти из него.
- Видит команды, доступные операторам или адресованные конкретно ему/операторам.
- Может запускать только команды, для которых отдельно разрешен запуск операторами и которые видимы ему.
- Не может создавать, изменять, удалять или публиковать команды.
- Не может запускать произвольные команды или команды, доступные только администратору.
- Видит результат и статус собственного запуска.

### Пользователь

- Может самостоятельно зарегистрироваться в приложении и войти/выйти.
- При регистрации получает роль `user`; выбрать или повысить роль самостоятельно нельзя.
- Может просматривать только команды, адресованные конкретно ему либо доступные всем пользователям.
- Не может запускать команды, открывать историю запусков или управлять командами.

### Администратор

- Имеет все права оператора.
- Может создавать, просматривать, изменять и удалять команды.
- Может запускать команды для отладки, в том числе до их публикации операторам.
- Может задавать для команды многострочный скрипт; редактирование и сохранение скриптов доступно только администраторам.
- Может добавлять к команде labels в формате `key:value` и задавать им цвет.
- Может настраивать области видимости команды: операторы, конкретные пользователи, конкретные операторы и все пользователи.
- Может отдельно разрешать или запрещать запуск команды операторами. Право просмотра не дает право запуска.
- Может удалять обычные учетные записи. Удаление учетной записи с ролью `admin` доступно только суперадминистратору с логином `admin`; нельзя удалить активную учетную запись или последнего администратора.
- Видит результаты собственных запусков и журнал действий пользователей.

Создание или отладочный запуск команды администратором не должны автоматически предоставлять к ней доступ операторам. Публикация для операторов выполняется отдельным явным действием.

## 3. Аутентификация и сессии

- Приложение должно показывать страницу входа с полями логина и пароля.
- Приложение должно предоставлять саморегистрацию по уникальному логину и паролю. Саморегистрация всегда создает роль `user`; роли `operator` и `admin` назначаются только через доверенную конфигурацию или администрирование.
- Логин должен содержать от 4 до 32 символов: латинские или кириллические буквы, цифры и символы `.`, `_`, `-`.
- Учетные записи хранятся в SQLite. Начальные учетные записи и их роли задаются конфигурацией и синхронизируются с базой при старте.
- Пароли должны храниться в виде стойких хешей. Если конфигурация задает пароль в открытом виде для первоначальной настройки, приложение не должно выводить его в логи или интерфейс.
- После успешного входа приложение создает серверную сессию и передает клиенту только случайный идентификатор сессии в cookie.
- Cookie сессии должна иметь флаги `HttpOnly` и `SameSite`; флаг `Secure` включается при работе по HTTPS.
- Сессия должна иметь ограниченный срок действия, завершаться при выходе пользователя и быть отозвана при смене учетных данных или перезапуске приложения, если хранилище сессий не является постоянным.
- Защищенные страницы и API должны проверять действительность сессии и роль пользователя на сервере. Скрытие элементов интерфейса не считается контролем доступа.
- Неуспешный вход должен возвращать понятное сообщение без раскрытия того, существует ли указанный логин.

## 4. Управление командами

Команда в приложении должна иметь:

- уникальный идентификатор и отображаемое название;
- описание назначения;
- исполняемый файл и аргументы либо иной явно определенный способ запуска;
- список параметров, если они предусмотрены, с типом, обязательностью и ограничениями;
- права просмотра: доступ операторам, конкретным пользователям, конкретным операторам и всем пользователям; области видимости можно комбинировать;
- отдельный признак, разрешающий операторам запуск команды;
- тайм-аут выполнения.

Администратор должен иметь возможность сохранить команду, выполнить ее в режиме отладки, просмотреть результат и отдельно настроить области видимости и право запуска операторами. Изменение команды должно сохраняться и отражаться в последующих запусках. Система должна валидировать конфигурацию команды и параметры до запуска.

Все команды и их настройки должны храниться в локальной базе данных SQLite. SQLite является источником истины для списка команд: создание, изменение, удаление и изменение доступности команды для операторов должны сохраняться в базе данных. После перезапуска приложения команды должны оставаться доступными в прежнем состоянии. Файл базы данных и схема должны создаваться или проверяться при запуске приложения.

Команда может задаваться либо многострочным скриптом, либо одним исполняемым файлом с аргументами; режимы взаимоисключающие. Скрипт запускается из временного файла через отдельный системный интерпретатор, заданный абсолютным путем в `script_interpreter` или выбранный по умолчанию для ОС. Пользовательский текст скрипта не конкатенируется в командную строку оболочки.

Команда может содержать labels `key:value` с цветом `#RRGGBB`. Редактор не создает пустые labels заранее: администратор добавляет строку кнопкой `+`. Цвет выбирается в компактной локальной панели у строки: пастельные пресеты, color picker или RGB-слайдеры. Каждая команда также может иметь значок, выбираемый в компактной сетке каталога распространенных действий (терминал, база данных, настройки, поиск, запуск, обновление и др.). SQLite хранит скрипт, labels, значок и имя последнего пользователя, запустившего каждую команду.

Приложение не должно передавать сформированную пользователем строку в системную оболочку. Исполняемый файл и аргументы следует запускать раздельно через API Go, с проверкой разрешенного набора исполняемых файлов и параметров. Произвольные shell-конструкции, подстановка команд и обход ограничений оператора должны быть запрещены.

## 5. Выполнение команд и результаты

- Запуск команды должен выполняться на сервере от имени учетной записи процесса приложения.
- Для каждого запуска должны фиксироваться пользователь, команда, время начала и завершения, итоговый статус и код возврата.
- Интерфейс должен показывать статус выполнения, стандартный вывод и ошибки команды.
- Пока команда выполняется, интерфейс должен показывать действие **«Прервать»**. Оно отправляет процессу системное прерывание: SIGINT группе процессов в Linux/macOS и CTRL_BREAK отдельной process group в Windows.
- Одна команда не может выполняться повторно, пока ее текущий запуск не завершился или не был прерван; разные команды могут выполняться параллельно.
- Должны поддерживаться тайм-аут и корректное завершение процесса по его истечении.
- Размер сохраняемого и отображаемого вывода должен быть ограничен конфигурацией.
- Секреты и пароли не должны попадать в журналы. Если команда получает чувствительные параметры, они должны маскироваться при отображении и журналировании.
- Ошибка выполнения команды не должна приводить к остановке веб-приложения.

## 6. Пользовательский интерфейс

Минимально необходимы следующие страницы:

- **Вход**: форма логина и пароля.
- **Регистрация**: создание учетной записи с ролью `user`.
- **Пользователи**: отдельная вкладка администратора со списком учетных записей и управлением ролями `user`, `operator` и `admin`.
- **Команды**: список доступных текущему пользователю команд и запуск команды.
- **Создание/изменение команды**: модальное окно администратора с редактором скрипта, ACL, выбором значка и labels; цвет открывается локально у строки label.
- **История запусков**: отдельный пункт меню и страница, доступная только `admin` и `operator`; операторы видят собственные запуски, администраторы могут фильтровать все запуски.
- После выполнения команда должна показывать имя последнего пользователя, который ее запускал.

При отсутствии доступа сервер должен возвращать отказ, а интерфейс — понятное сообщение. После выхода пользователь должен быть перенаправлен на страницу входа.

### Визуальный стиль

- Интерфейс должен быть максимально светлым, минималистичным и функциональным, по общему визуальному направлению и плотности элементов приближенным к Metabase.
- Использовать белый или очень светлый фон, нейтральные поверхности, тонкие разделители и сдержанный акцентный цвет. Контраст текста и элементов управления должен оставаться достаточным для комфортного чтения.
- Предпочитать компактную боковую навигацию и ясную основную рабочую область. Списки команд и журнал запусков представлять в виде легко сканируемых таблиц с поиском и фильтрами там, где они предусмотрены.
- Избегать декоративных градиентов, тяжелых теней, крупных карточек и избыточных украшений. Визуальные акценты использовать для статусов, ошибок и основных действий.
- Сохранять единообразие отступов, типографики, кнопок и форм. Интерфейс должен оставаться читаемым и удобным на узких экранах.
- Использовать Metabase только как референс общего характера: не копировать его логотип, фирменные иллюстрации или уникальные брендовые элементы.

## 7. Конфигурация и эксплуатация

- Настройки приложения должны загружаться из файла конфигурации и/или переменных окружения.
- Конфигурация должна включать адрес и порт HTTP-сервера, путь к локальному файлу SQLite, пользователей и их роли, параметры сессий, тайм-ауты команд, лимит вывода, список разрешенных исполняемых файлов и необязательный абсолютный путь `script_interpreter`.
- Путь к файлу SQLite по умолчанию должен указывать на локальный каталог данных приложения; каталог должен создаваться при необходимости. Путь можно переопределить конфигурацией.
- Приложение должно использовать параметризованные SQL-запросы и обрабатывать ошибки открытия базы данных, миграций и операций чтения/записи без потери молчаливого состояния.
- Секреты не должны храниться в репозитории. Для рабочей среды следует использовать переменные окружения или защищенное хранилище секретов.
- Некорректная или неполная конфигурация должна приводить к понятной ошибке при старте, а не к запуску с небезопасными значениями по умолчанию.
- Приложение должно корректно завершать HTTP-сервер и активные процессы при получении сигнала остановки.
- Для работы по сети вне локальной доверенной среды должен использоваться HTTPS через TLS непосредственно в приложении или через доверенный обратный прокси.
- Сохраненный скрипт запускается отдельным системным интерпретатором из временного файла, без конкатенации в командную строку shell. На Windows по умолчанию применяется PowerShell без профиля, на Unix-подобных системах — `/bin/sh`; интерпретатор можно задать через `script_interpreter`.
- Редактировать и сохранять скрипты может только администратор. Оператор запускает только уже сохраненный скрипт, если он видим ему и включено отдельное право запуска; роль `user` запускать не может.

## 8. Нефункциональные требования

- Серверная часть реализуется на Go.
- Приложение должно иметь тесты на аутентификацию, проверку ролей, управление доступностью команд, сохранение команд в SQLite и запуск команд.
- Приложение должно проверять сохранение script, labels и последнего пользователя запуска в SQLite после повторного открытия базы.
- Проверки доступа должны выполняться на сервере для каждого действия.
- Роль `user` не может запускать команды ни через интерфейс, ни прямым запросом к серверу.
- Право оператора просматривать команду и право запускать ее проверяются отдельно.
- Ошибки приложения и ключевые действия должны журналироваться без учетных секретов.
- Время выполнения команды и размер вывода должны быть ограничены настройками; число одновременных процессов ограничивается запретом повторного запуска одной команды.
- Каждый активный запуск команды может быть прерван администратором через системное событие/сигнал.

## 9. Критерии приемки

1. Пользователь с неверным логином или паролем не получает сессию; успешный вход устанавливает cookie с настроенными защитными флагами.
2. После выхода cookie-сессия больше не дает доступ к защищенным страницам и API.
3. Саморегистрация всегда создает роль `user`, не позволяя выбрать повышенную роль.
4. Логин принимает от 4 до 32 символов, включая кириллицу, латиницу и цифры; неподдерживаемые символы отклоняются.
5. Администратор видит список пользователей и может менять их роли; последний администратор не может лишиться административной роли.
6. Пользователь `user` видит команды по ACL, но не получает возможность запускать их или просматривать историю запусков.
7. История открывается отдельным маршрутом для ролей `admin` и `operator`; роль `user` получает отказ при прямом запросе.
8. Все четыре области видимости работают независимо и проверяются сервером: операторы, конкретные пользователи, конкретные операторы и все пользователи.
9. Просмотр команды оператором не разрешает ее запуск без отдельного права на запуск.
10. Оператор не может создавать или изменять команды даже при прямом вызове соответствующего API.
11. Администратор может создать команду в модальном окне, сохранить многострочный скрипт, назначить labels и настроить цвет каждой метки.
12. Скрипт запускается выбранным/настроенным интерпретатором без shell-строкового конкатенирования; соблюдаются тайм-ауты и лимиты вывода.
13. После запуска команда отображает последнего пользователя и UTC-время последнего запуска.
14. Созданная или измененная команда, скрипт, labels, ACL и последний пользователь запуска сохраняются в SQLite после перезапуска приложения.
15. В истории запуска фиксируются пользователь, результат и снимок исходного скрипта либо исполняемого файла с аргументами; тайм-аут и ошибка процесса отображаются корректно.
16. Во время выполнения администратору доступна кнопка «Прервать»; оператор не может прерывать запуски. Новый запуск до завершения текущего получает отказ, а после системного прерывания сохраняется статус `interrupted`.
17. Секреты отсутствуют в логах и отображаемых результатах.

## 10. Вне рамок первой версии

- Восстановление пароля.
- Интеграция с LDAP, Active Directory, OAuth или SSO.
- Распределенное выполнение команд на удаленных хостах.
- Многофакторная аутентификация.

## 11. Локальный запуск прототипа

1. Скопировать `config.example.json` в `config.json` и заменить демонстрационные пароли длинными уникальными значениями.
2. Проверить, что пути в `allowed_executables` абсолютные и указывают на исполняемые файлы, которым разрешено запускаться. Операторские команды запускаются только из этого списка.
3. Запустить приложение командой `make run` из корня проекта. Цель соберет бинарник и запустит сервер; по умолчанию интерфейс будет доступен по адресу `http://127.0.0.1:8080`.
4. Для другого файла конфигурации задать переменную окружения `CMDUI_CONFIG` с путем к JSON-файлу.
5. Перезапустить сервер командой `make restart` или остановить его командой `make stop`.
6. Проверить проект командой `make test` (или `go test ./...`).

## 12. Структура проекта

- `cmd/server`: композиция зависимостей, запуск HTTP-сервера и graceful shutdown.
- `internal/api`: HTTP-маршруты, middleware сессий/CSRF и преобразование ошибок сервисов в HTTP-ответы.
- `internal/config`: чтение и валидация конфигурации приложения.
- `internal/domain`: общие модели пользователей, команд и запусков.
- `internal/service/auth`: вход, регистрация, bootstrap учетных записей и управление ролями.
- `internal/service/commands`: ACL, проверка исполняемых файлов, запуск процессов и история запусков.
- `internal/repository/users`, `internal/repository/commands`, `internal/repository/runs`: контракты репозиториев.
- `internal/repository/sqlite`: SQLite-схема, миграции и реализация репозиториев.
- `ui`: HTML-шаблоны и представления интерфейса, отдельно от HTTP-обработчиков.

Прототип хранит учетные записи, команды, ACL и историю запусков в SQLite. Саморегистрация создает пользователя с правами только на просмотр. Cookie-сессии хранятся в памяти процесса и поэтому становятся недействительными после перезапуска приложения. Пароли конфигурации и регистрации хранятся только в виде bcrypt-хешей; сам файл `config.json` исключен из Git.
